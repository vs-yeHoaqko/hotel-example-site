**Input**: Design documents from
`evaluation/specs/015-guided-harness-onboarding/`
**Prerequisites**: plan.md, spec.md, research.md, data-model.md, contracts/,
quickstart.md

**Tests**: Include focused unit and CLI validation tasks because this feature
adds testable evaluation-harness behavior.

`.specify/feature.json` and `AGENTS.md` active-feature pointers.

implemented and tested independently after the foundational model is complete.

- **[P]**: Can run in parallel (different files, no dependencies)

## Dependencies & Execution Order

### Phase Dependencies

- **Setup (Phase 1)**: No dependencies.
- **Foundational (Phase 2)**: Depends on setup files from Phase 1 and blocks all
  user stories.
- **User Story 1 (Phase 3)**: Depends on foundational model/report helpers.
- **User Story 2 (Phase 4)**: Depends on foundational model/report helpers and
  can validate example state even if US1 CLI is incomplete.
- **User Story 3 (Phase 5)**: Depends on US1 draft/write behavior and
  foundational merge support.
- **Polish (Phase 6)**: Depends on desired stories being complete.

### User Story Dependencies

- **US1 (P1)**: MVP; can start after Phase 2.
- **US2 (P2)**: Can start after Phase 2; integrates naturally after US1 but
  remains testable with example/fixture adapter states.
- **US3 (P3)**: Requires US1 write/re-run flow, but remains independently
  testable with saved-state fixtures.

- T003, T004, and T005 can run in parallel after T001/T002 decisions are clear.

  stable.

## Implementation Strategy

### MVP First (User Story 1 Only)

1. Complete Phase 1: Setup.
2. Complete Phase 2: Foundational model/report helpers.
3. Complete Phase 3: guided discovery and draft adapter creation.
4. Stop and validate dry-run/write behavior before adding full readiness gates.

### Incremental Delivery

1. US1 creates reviewable adapter drafts.
2. US2 validates readiness and renders the review summary.
3. US3 preserves decisions across re-runs and conflict cases.
4. Polish runs full tests, formatting, quickstart validation, and boundary
   review.

### Boundary Reminder

This feature does not generate GitHub Actions workflows, run evidence layers,
thin E2E tests, mutate product files, or introduce repair mode.
