# Evaluation Harness Commonization Blueprint

## Scope And Non-Goals

This blueprint defines how the current `evaluation/` harness should be split
between reusable common behavior and repository-local policy before any shared
code is extracted.

The decision this blueprint supports is narrow: identify what can safely become
shared harness capability, what must be supplied by an adopter through
configuration or adapters, and what should remain local to this fork unless a
later specification promotes it.

Non-goals for 014:

- Do not extract a package, publish a library, or create a shared CLI.
- Do not move or edit runtime harness modules under `evaluation/bin/`,
  `evaluation/lib/`, `evaluation/config/`, or `evaluation/tests/`.
- Do not change product source, product fixtures, static pages, root package
  scripts, root browser-test configuration, or root E2E source files.
- Do not change `.github/workflows/evaluation.yml` behavior.
- Do not change upstream push behavior.
- Do not commit generated `evaluation/runs/` artifacts.
- Do not introduce automatic repair mode.
- Do not thin, rewrite, or remove any E2E assertions.

Accepted research decisions:

- 014 is a blueprint feature, not the first runtime extraction.
- Capabilities are classified by commonization boundary, not by directory or
  implementation effort.
- The adopter workflow is a first-class contract because correct process is
  part of harness trust.
- Missing, weak, warning, unknown, and unmapped evidence must stay visible.
- E2E thinning remains behind readiness gates.
- Markdown contracts are sufficient for this planning feature.
- Active pointer edits are limited to `.specify/feature.json` and `AGENTS.md`.

## Capability Classification

Allowed classifications:

- `reusable-core`: behavior that should be shared after adapter boundaries are
  reviewed.
- `adapter-contract`: adopter-provided configuration, commands, paths, or
  policies required by reusable behavior.
- `project-policy`: reviewed local choice that should not become a shared
  default.
- `generated-evidence`: output produced by the harness and consumed by humans
  or later automation.
- `intentionally-local`: repository context or guardrail that should remain
  outside shared code.

Allowed decisions:

- `keep-shared`
- `parameterize`
- `generate-locally`
- `keep-local`
- `defer`
- `exclude`

## Guided Onboarding Workflow

Status semantics:

- `pass`: the step produced enough evidence to continue.
- `warning`: the step can continue, but a reviewer must inspect the finding.
- `unknown`: evidence is missing or partial and must remain visible.
- `blocked`: the process must stop until a required condition is resolved.
- `deferred`: the step is intentionally postponed with a recorded reason.
- Weak-signal and unmapped evidence must remain visible and must not be counted
  as passing coverage.

| ID    | Name                            | Goal                                                          | Required input                                                                      | Expected output                                                   | Validation signal                                                             | Stopping condition                                            | Next action on pass                  | Next action on warning                       | Next action on blocked                         |
| ----- | ------------------------------- | ------------------------------------------------------------- | ----------------------------------------------------------------------------------- | ----------------------------------------------------------------- | ----------------------------------------------------------------------------- | ------------------------------------------------------------- | ------------------------------------ | -------------------------------------------- | ---------------------------------------------- |
| `W01` | Repository inspection           | Establish the local system under test and governance boundary | Repository root, product/test layout, package manager, CI policy, ignored paths     | Initial source inventory and out-of-scope list                    | Existing tests, build commands, ignore files, and CI files are identified     | Stop if product ownership or allowed edit boundary is unknown | Proceed to test layer discovery      | Record uncertain ownership as warning        | Resolve governance boundary before configuring |
| `W02` | Test layer discovery            | Identify available evidence layers                            | Test roots, commands, existing configs                                              | Candidate layer list and source labels                            | Each discovered layer has a command or explicit deferred reason               | Stop if no runnable layer exists                              | Proceed to preflight                 | Continue with partial layers marked unknown  | Define at least one runnable evidence layer    |
| `W03` | Environment preflight           | Prove local tools can run                                     | Required tools and tool checks                                                      | Preflight artifact with pass/fail checks                          | Required tool checks pass or fail with guidance                               | Stop on missing required runtime                              | Configure local adapter              | Review optional missing tools                | Install/fix required tools                     |

Edge case handling:

- If a repository has no browser tests, browser layers should be absent or
  deferred; reports must not fail solely because browser evidence is absent.
- If a repository has no unit tests, unit ownership and lower-layer evidence are
  `unknown` until a local owner layer is defined.
- If only one test layer exists, the harness can still run, but thinning and
  owner-layer claims stay blocked.
- If a monorepo has multiple apps, each app needs either a separate adapter or a
  named target within one adapter.
- If tests run but emit no structured results, latest status may come from
  layer status while test-level coverage remains `unknown`.
- If generated artifacts are not ignored, onboarding is blocked until ignore
  rules are corrected.
- If feature mappings cannot be inferred confidently, unmapped evidence remains
  visible and feature rows stay `unknown`.
- If latest evidence passes but historical warnings exist, rows may be `warn`
  without becoming `fail`.
- If CI is absent, the harness can operate locally, but artifact retention and
  first-screen review are warning-level gaps.
- If local security or privacy policy conflicts with shared defaults, the local
  policy wins and the adapter records the override.
